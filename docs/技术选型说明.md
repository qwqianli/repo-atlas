# repo-atlas 技术选型说明

> 协作约定：本文件只讲「选什么 / 为什么选 / 各管哪一段」，**不写业务实现**。业务代码由你写。

---

## 0. 先明确这个东西到底在干什么

**输入**：一个 Git 仓库地址（或本地路径）
**输出**：一份"项目导读"——这个项目是干什么的、文件怎么分层、谁依赖谁、按什么顺序读、每个模块一句话说明。

一句话概括：

> 把「读不懂一个陌生仓库」这件事，拆成 **解析 → 理解 → 呈现** 三段流水线。

三段分别吃不同的技术，这就是整份选型文档的骨架：

| 段 | 干什么 | 主要靠什么 |
|---|---|---|
| 解析 | clone 仓库、遍历文件、用 AST 提取 import 依赖 | Python 标准库（`ast` / `pathlib` / `subprocess`） |
| 理解 | 把模块代码喂给大模型，换回一段人话说明 | 任意 OpenAI 兼容接口 + 本地缓存 |
| 呈现 | 文件树 + 依赖图 + 阅读路线 + 实时进度条 | Vue 3 / AntV G6 / SSE |

**这三个阶段的边界是硬的**：解析只产出结构化数据（JSON），理解只消费结构化数据，呈现只消费接口返回。任何一段都可以单独替换掉（比如以后把 LLM 换成别的模型，前端一行都不用改）。

### 2.1 Vue 3

**是什么**
一个把页面拆成"组件"的前端框架。一个组件 = 一块 HTML 模板 + 一段 JS 逻辑 + 一点样式，装在 `.vue` 单文件里。

Vue 3 相比 Vue 2 的关键变化是 **Composition API**：逻辑可以按功能组织（而不是按 `data / methods / computed` 分块塞），并且可以抽出来复用（抽出来的东西叫 **composable**，约定 `useXxx.js` 命名）。

**不用它会怎样**
用原生 JS 操作 DOM 的话，你要自己写 `document.querySelector('#tree').innerHTML = ...`，数据一变就得手动同步界面。文件树、依赖图这种数据频繁变化的地方，手写 DOM 同步会失控。

**在本项目里干什么**

| 页面对应 | 组件 | 干什么 |
|---|---|---|
| 首页 | `RepoInput.vue` | 输入框 + "开始分析"按钮 |
| 结果页 | `FileTree.vue` | 左侧递归文件树（**递归组件**，自己套自己） |
| 结果页 | `DependencyGraph.vue` | 中间 G6 画布 |
| 结果页 | `ModuleDetail.vue` | 点节点后右侧显示 AI 写的说明 |
| 结果页 | `ReadingPath.vue` | 底部阅读顺序列表 |
| 全局 | `useAnalysis.js` | composable：封装"发起分析 + 接 SSE + 更新进度" |

**最小可跑例子**（理解 `.vue` 单文件和 Composition API 长什么样）：

```vue
<script setup>
import { ref, computed } from 'vue'

const files = ref(['app.py', 'models.py'])
const count = computed(() => files.value.length)
</script>

<template>
  <p>共 {{ count }} 个文件</p>
  <ul><li v-for="f in files" :key="f">{{ f }}</li></ul>
</template>
```

`ref` = 响应式数据（改了界面自己变）；`computed` = 派生值（依赖变了自动重算，**不要用函数代替 computed**）。

**坑**

- `ref` 在 JS 里要用 `.value` 取值，在模板里不用。这是最常见的坑。
- `v-for` 必须给 `:key`，且不要用 index 当 key（列表会重排时状态会错位）。

### 2.2 Vite

**是什么**
前端构建工具。干两件事：**开发时**起一个本地服务器，改代码保存后浏览器自动热更新（毫秒级）；**上线时**把 `.vue` / `.js` / `.css` 打包压缩成浏览器能直接跑的静态文件。

它快的原因：开发阶段**不打包**，浏览器要哪个模块就现编哪个模块（基于浏览器原生 ESM）。

**不用它会怎样**
要么手动写 `webpack.config.js` 配一堆 loader 等几十秒编译，要么干脆不能用 `.vue` 单文件格式。

**在本项目里干什么**

1. 起前端开发服务器（默认 `5173` 端口）
2. **配置代理解决跨域**——这是本项目必须做的一步：

```js
// vite.config.js
export default {
  server: {
    port: 5173,
    proxy: {
      // 前端请求 /api/xxx → 转发到 http://127.0.0.1:5000/api/xxx
      '/api': { target: 'http://127.0.0.1:5000', changeOrigin: true }
    }
  }
}
```

**跨域这件事必须讲清楚**（最常见的坑）：

- 浏览器有 **同源策略**：`5173` 页面里的 JS 不能直接读 `5000` 的响应（端口不同就算跨源）。
- 配了 Vite 代理后，浏览器以为在请求自己的 `5173/api/...`，**由 Vite 这个 Node 进程替你去请求 5000**，再把结果返回给浏览器。Node 进程之间没有同源策略，所以不会被拦。
- 这也是为什么 Flask 那边**不需要**装 `flask-cors`——代理已经把跨域问题绕过了。生产环境用 Nginx 做同样的事（`proxy_pass`）。

**坑**
`changeOrigin: true` 不能漏，否则后端收到的 `Host` 头是 `localhost:5173`，某些校验会挂。

### 2.3 Flask

**是什么**
Python 的轻量 Web 框架。核心只有一句：**把 URL 映射到 Python 函数**。

```python
@app.get("/api/repos")
def list_repos():
    return {"code": 0, "data": [...]}
```

**不用它会怎样**
要用 Python 手写 HTTP 服务器（解析请求行、头、body），几千行起步。

**在本项目里干什么**

它只干三件事：**收请求 → 调 service → 返回统一格式**。它**不写业务逻辑**。

分层（这个分层是项目的核心设计，也是本项目最核心的设计）：

```
api/          ← 路由层：只做参数校验 + 调 service + 组装响应，不写业务
services/     ← 业务层：编排 analyzer 和 LLM，唯一允许抛 BusinessError 的地方
analyzer/     ← 分析层：纯函数式的代码解析，不依赖 Flask
models        ← 数据层：SQLite 表结构
```

为什么要这么分？三个具体好处：

1. **analyzer 可以脱离 Flask 单测**——`pytest` 直接 `from analyzer.ast_parser import extract_imports` 就能测，不用起服务器。
2. **换框架成本为零**——业务逻辑不认识 Flask，将来换 FastAPI 只改 `api/` 那一层。
3. **业务报错可以用单元测试秒级覆盖**（36 种状态流转组合这种，不用发 36 次 HTTP 请求）。

**为什么是 Flask 不是 FastAPI / Django**

| | Flask | FastAPI | Django |
|---|---|---|---|
| 上手成本 | 低，一个文件能跑 | 中，要懂 async / Pydantic | 高，一上来就是一套工程规范 |
| 异步能力 | 同步为主（够用） | 原生 async（强） | 同步 + 3.0 起支持 async |
| 自带功能 | 几乎没有（要自己拼） | 自动生成接口文档 | ORM / Admin / 认证全都有 |
| 适合本项目吗 | ✅ 合适 | 也合适，但要额外学 async | ❌ 太重，学 Django 的时间够写完项目了 |

**选 Flask 的真实理由**：本项目的瓶颈是「git clone + 调 LLM 等网络」这类 IO，用线程池就能解决，**不需要 async 那套复杂度**。而且 Flask 的"什么都不给你"，正好逼你自己搭分层——这恰恰是这个项目要练的东西。Django 那种"什么都给你"的框架，会让人写完项目还是不知道各层在干嘛。

**注意**：用户此前明确表示"嫌 Django 复杂，偏好 Flask"，选 Flask 也符合既有技术栈（bilibili-test 就是 Flask）。

### 2.4 线程池 + GIL（本项目最容易讲出深度的一块）

**是什么**
`ThreadPoolExecutor` 是标准库里现成的线程池：开 N 个线程，把任务丢进去排队执行，主线程不用一个个等。

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(analyze_one, repo) for repo in repos]
    for f in futures:
        print(f.result())      # 谁先完成先拿谁的结果
```

**为什么需要它**
分析一个仓库要串行做很多"等待"：`git clone` 等网络（几秒到几十秒）、每个模块调 LLM 等响应（每个 1~5 秒）。40 个模块串行 = 几分钟，用户会以为页面卡死了。开 4~8 个线程并行等，总耗时降到几分之一。

**关键概念：GIL**

Python 有个全局解释器锁（GIL），**同一时刻只允许一个线程执行 Python 字节码**。所以：

| 任务类型 | 例子 | 线程池有用吗 |
|---|---|---|
| **IO 密集** | `git clone`、HTTP 调 LLM、读文件、查数据库 | ✅ 非常有用。线程在等网络时会主动释放 GIL，别的线程就能跑 |
| **CPU 密集** | AST 解析、正则匹配、加密计算 | ❌ 没用。抢不到 GIL，还多了线程切换开销，可能比串行更慢 |

**所以本项目的正确做法**：

- **线程池只包 IO 部分**：git clone、调 LLM、读写文件 → 这些放进池子
- **AST 解析部分串行做**（或者以后优化时换成 `ProcessPoolExecutor` 多进程，绕开 GIL）

这个区分是理解 Python 并发的关键。**能说清 GIL 的边界，比会用线程池重要得多。**

**坑**

- `max_workers` 别开太大（比如 50）：LLM 接口有 QPS 限流，开太多会大面积 429，还会把自己的免费额度打爆。**4~8 是合理区间。**
- 线程池里的异常不会自动冒出来，必须 `f.result()` 才会抛。要统一收集，不然任务默默失败了你还以为成功。

### 2.5 SQLite

**是什么**
一个**单个文件就是一个数据库**的嵌入式数据库。Python 标准库自带 `sqlite3`，不用装任何服务、不用配账号密码、不用占端口。

**在本项目里干什么**

不是为了"用上数据库"，而是为了这两个具体收益：

1. **缓存**。同一个仓库分析第二次时，直接读库里的结果，**不重复烧 token**。这是最实在的省钱功能。
2. **历史记录**。首页能列出"你分析过的仓库"，点进去直接看。

表大概长这样（3 张，不复杂）：

| 表 | 存什么 |
|---|---|
| `repo` | 仓库地址、分支、最近分析时间、状态 |
| `module` | 每个文件/模块的路径、依赖列表、AI 说明 |
| `analysis_task` | 每次分析的进度、耗时、消耗 token 数 |

**为什么不是 MySQL**

| | SQLite | MySQL |
|---|---|---|
| 部署 | 零，文件跟着项目走 | 要装服务、建库、建用户、配权限 |
| 端口 | 不占 | 占 3306 |
| 并发写 | 弱（写会锁整个库） | 强 |
| 适合场景 | 单机、单用户、读多写少 | 多用户、高并发、网络访问 |

**两个具体理由**（都值得讲清楚）：

1. 本项目是**单用户单机工具**，不存在并发写压力，SQLite 完全够。上 MySQL 是"为了简历上有个 MySQL"而加戏。
2. 本机 **3306 端口已经被禅道（含喧喧）占着**，硬上 MySQL 要先解决端口冲突——纯属给自己制造麻烦。

**更重要的是**：这一层刻意做成可切换——连库参数收在 `config.py` 里，将来真要换 MySQL，**只改一行连接串 + 换 ORM 的方言**，业务代码不动。这就是"分层带来的可替换性"的实证。

### 2.6 AntV G6

**是什么**
蚂蚁开源的关系图（图可视化）引擎。给它 `nodes` + `edges`，它负责布局（自动算坐标）和渲染（画到 Canvas 上），还带缩放、拖拽、点选、高亮这些交互。

**不用它会怎样**
要么自己用 Canvas 手画线（坐标要自己算，缩放拖拽要自己实现），要么只能用 `ECharts` 的 graph 类型硬凑（布局能力弱，节点一多就糊）。

**在本项目里干什么**

把 `ast` 解析出来的 import 关系画成一张图：

- **节点** = 一个 .py 文件
- **边** = "A import 了 B"
- **布局** = `dagre`（分层布局，从左到右），能直观看出"谁是被依赖最深的底层模块"
- **点击节点** = 右侧面板显示该模块的 AI 说明（`graph.on('node:click', ...)`）

**最小可跑例子**（G6 5.x 的写法）：

```js
import { Graph } from '@antv/g6'

const graph = new Graph({
  container: 'graph-mount',        // 一个 <div id="graph-mount">
  data: {
    nodes: [{ id: 'app.py' }, { id: 'models.py' }],
    edges: [{ source: 'app.py', target: 'models.py' }]
  },
  layout: { type: 'dagre', rankdir: 'LR' },
  node: { style: { labelText: (d) => d.id } },
  behaviors: ['zoom-canvas', 'drag-canvas', 'drag-element']
})
graph.render()
```

**为什么是 G6 不是 D3 / ECharts**

| | G6 | D3 | ECharts |
|---|---|---|---|
| 定位 | 专做关系图 | 底层可视化库（什么都能画，但什么都要自己写） | 主打统计图表 |
| 上手 | 中，配置式 | 陡，要懂 SVG / 力导向数学 | 易，但关系图不是它强项 |
| 力导向/分层布局 | 内置多种 | 要自己组合 | 弱 |

选 G6 的核心理由：**这个项目 90% 的可视化工作就是"画一张关系图"**，用专门工具最省时间。D3 更适合"我要做一个前所未有的可视化"的场合。

**坑**

- G6 5.x 和 4.x **API 不兼容**（4.x 用 `graph.data(); graph.render()`，5.x 用 `new Graph({ data })`。查文档一定要看清楚版本号，网上大量 4.x 的例子会误导你。
- 节点多了（几百个）会卡，需要开 `layout: { type: 'dagre' }` 配合折叠/过滤。本项目先不做，留作优化点。

### 2.7 SSE（Server-Sent Events）

**是什么**
一种"服务器单向往前端持续推消息"的 HTTP 技术。就是普通的 HTTP 响应，只是 `Content-Type` 是 `text/event-stream`，连接**不关闭**，后端可以一直往里写。

浏览器侧用一行原生 API 就能接：

```js
const es = new EventSource('/api/tasks/123/stream')
es.onmessage = (e) => {
  const { stage, done, total } = JSON.parse(e.data)
  progress.value = total ? Math.round((done / total) * 100) : 0
}
```

后端侧就是往响应流里写固定格式的文本（**两个换行** 表示一条消息结束）：

```
data: {"stage":"parse","done":12,"total":40}

data: {"stage":"llm","done":18,"total":40}

```

**在本项目里干什么**

分析一个仓库要几十秒。**不能让用户盯着转圈圈**——要显示"正在 clone → 正在解析 12/40 → 正在生成说明 18/40"。这个进度只有后端知道，必须由后端主动推给前端。SSE 就是干这个的。

**为什么是 SSE 不是 WebSocket**

| | SSE | WebSocket | 轮询（前端每 2 秒问一次） |
|---|---|---|---|
| 方向 | 后端 → 前端 单向 | 双向 | 前端 → 后端 |
| 协议 | 就是 HTTP | 独立协议（要升级握手） | HTTP |
| 浏览器 API | `EventSource`（原生） | `new WebSocket()` | `setInterval` + `fetch` |
| 断线重连 | **自动重连** | 要自己写 | 天然就是重连 |
| 后端复杂度 | 低（一个普通视图函数） | 高（要管连接池、心跳） | 最低 |
| 适合场景 | 进度条、日志流、通知 | 聊天、协同编辑、游戏 | 状态变化不频繁 |

**选 SSE 的理由**：本项目只需要"后端告诉前端进度"这一个方向，**根本不需要双向通信**。用 WebSocket 是杀鸡用牛刀，还得处理连接存活、心跳、断线诊断。SSE 是纯 HTTP，Flask 里就是一个普通的流式响应，调试时用 `curl` 都能直接看。

**轮询为什么不行**：每次轮询都是一次完整请求（带全部请求头），40 秒的任务要发 20 次请求，一半是空转。而且进度更新有一两秒延迟。SSE 是一次连接、持续推送、零延迟。

**坑（这个一定会踩）**

1. **Flask 需要 `stream_with_context`**，否则视图函数返回后请求上下文就被销毁了，流里访问 `request` / `current_app` 会报错。
2. **生产环境 Nginx 默认会缓冲响应**，导致所有进度一次性吐出来（等于没做）。要加响应头 `X-Accel-Buffering: no`。
3. `EventSource` **不能自定义请求头**（不能带 `Authorization`）。带登录态的项目一般改用 fetch + ReadableStream，但本项目单机无登录，用 `EventSource` 最省事。

## 3. 关键取舍速查表

把上面散落的对比收成一张表，动手选型前扫一眼：

| 决策点 | 选了 | 没选 | 一句话理由 |
|---|---|---|---|
| Web 框架 | Flask | FastAPI / Django | 瓶颈是 IO 不需要 async；Django 太重，会跳过"自己分层"这个练习 |
| 数据库 | SQLite | MySQL | 单机单用户无并发写；且本机 3306 被禅道占着 |
| 进度推送 | SSE | WebSocket / 轮询 | 只需单向推送；SSE 是纯 HTTP 且自动重连 |
| 图可视化 | AntV G6 | D3 / ECharts | 90% 的工作就是画关系图，专用工具最省时 |
| 并发模型 | 线程池（只包 IO） | 多进程 / asyncio | clone 和调 LLM 都是 IO 密集；AST 那点 CPU 串行完全够 |
| 前端构建 | Vite | Webpack | 开发热更新毫秒级，配置几乎为零 |
| 前端框架 | Vue 3 | React | 已有 Vue 基础；单文件组件更直观 |

## 4. 三条可复用的选型原则

这三条比具体选了哪个技术更值钱，因为它们能迁移到任何项目：

1. **按瓶颈选技术，不按简历选技术。**
   本项目瓶颈是"等网络"，所以线程池就够，不需要 async。反过来，如果一个项目真的是 CPU 密集（比如视频转码），那就必须上多进程/Celery，而不是硬用线程池。**先问瓶颈在哪，再问该用什么。**

2. **能被替换的才是好设计。**
   SQLite 换 MySQL 只改一行连接串、LLM 换供应商只改一个适配器、前端完全不知道后端语言——这些都是**故意设计出来的可替换性**。被问「你的设计有什么优点」时，答「这里换 X 只需要改 Y」比答「我用了设计模式」有力得多。

3. **每引入一个依赖，都要能说出"不用它会怎样"。**
   说不出就说明可以不引入。这一条能挡掉 80% 的技术栈膨胀。

---

## 5. 明确「不引入」的东西（反选型）

这份清单和上面同等重要——**限定范围比扩展范围更能保证项目做完**：

| 不引入 | 原因 |
|---|---|
| Redis | 没有缓存热点，SQLite 的缓存表就够 |
| Celery / 消息队列 | 单机单用户，线程池就是最简的任务队列 |
| WebSocket | 见 2.7 |
| MySQL | 见 2.5 |
| Docker | 本地跑得通就是目标；部署留到以后再说，那时你会发现多一层容器只是多一层调试成本 |
| 用户登录 / 鉴权 | 单机工具，加鉴权只会让 SSE 那块变复杂（`EventSource` 不能带 header） |
| TypeScript | 前端只有两个页面，为它配类型会拖慢进度。**以后想加再加** |
| 微服务 / 多模块拆分 | 一个 Flask 进程 + 一个 Vite 进程，就是最合适的粒度 |

**判断标准**：每个不引入的项，都要能回答"去掉它，项目会少什么功能？"——如果答案是"没有"或"只是简历上少个词"，那就不引入。

## 7. 每个技术对应一句「核心要点」

这张表是这份文档的真正用途——**每学完一块，就回来把这行填成自己的话**。

| 技术 | 常见疑问 | 该讲清的点 |
|---|---|---|
| Vue 3 | 组件的状态怎么管理？ | `ref` 响应式 + `computed` 派生 + composable 抽复用逻辑 |
| Vite | 前后端分离怎么解决跨域？ | 同源策略 → 开发用 Vite proxy、生产用 Nginx 反代；后端不需要 CORS |
| Flask | 你的项目怎么分层？为什么这么分？ | api / services / analyzer 三层；analyzer 能脱离框架单测；换框架成本为零 |
| 线程池 + GIL | 多线程在 Python 里有用吗？ | IO 密集有用（等网络时释放 GIL），CPU 密集没用；所以要区分任务类型 |
| SQLite | 为什么不用 MySQL？ | 单机单用户无并发写；换 MySQL 只改连接串，是真做过可替换设计的 |
| AntV G6 | 为什么选这个可视化库？ | 需求是关系图，专用库；D3 更适合自定义可视化，ECharts 关系图能力弱 |
| SSE | 实时进度怎么实现的？为什么不用 WebSocket？ | 只需单向推送；SSE 是纯 HTTP、自动重连、后端一个视图函数搞定 |
